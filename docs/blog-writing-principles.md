# 블로그 글쓰기와 재작성 원칙

2026-10-26에 합의한 기준이다. 글을 작성하거나 재작성하기 전에 이 문서를 읽고, 초안 완성 뒤에도 대조한다.
문체의 근거는 「감시자를 감시하는 감시자를 감시하는 감시자를..」와 「여보세요? 음성 통화 서버를 구축하고 싶습니다」를 제외한 기존 공개 글 102편이다.
이 기준은 블로그 본문에 적용한다. UI의 짧은 라벨 작성 규칙을 설명문 전체에 적용하지 않는다.

이 블로그는 공부하고 구현하면서 생긴 의문을 독자와 함께 풀어가는 방식으로 쓴다. 원래 글에 담긴 경험과 판단을 보존하면서 독자가 이해하기 어려웠던 설명과 부정확한 내용을 고친다.

## 글을 쓰는 방법

1. **글에서 해결할 질문을 먼저 정한다.** 무엇이 궁금했는지, 어떤 문제가 생겼는지, 왜 이 내용을 공부했는지부터 확인한다. 도입부에는 본문을 이해하는 데 필요한 계기만 적는다.
2. **생각이 진행된 순서가 드러나게 쓴다.** 처음 생각, 시도, 막힌 부분, 알게 된 내용을 연결한다. 실제로 하지 않은 시행착오나 경험은 만들지 않는다. 경험이 없는 개념 설명에 개인 서사를 억지로 추가하지 않는다.
3. **개념을 소개한 뒤 구체적으로 설명한다.** 정의에서 끝내지 않고 코드, 입력과 출력, 실제 상황, 익숙한 비유로 작동 방식을 설명한다. 예시 뒤에는 독자가 무엇을 봐야 하는지 짚는다.
4. **독자의 다음 의문을 설명에 활용한다.** “그냥 이렇게 하면 안 될까?”, “무조건 좋은 방법일까?” 같은 질문 뒤에 실제 이유나 조건을 설명한다. 모든 문단을 문답 형식으로 만들지는 않는다.
5. **기존의 설명체를 유지한다.** 기본 어미는 “~이다”, “~한다”, “~된다”로 쓴다. “알아보자”, “해보자”, “그럼”, “일단”, “이렇게 하면”은 흐름에 필요하면 사용한다. 공지처럼 용도가 다른 글의 말투는 존중한다.
6. **개인적인 판단에는 이유를 붙인다.** 어떤 방법이 편했는지, 왜 선택했는지, 무엇이 불편했는지 적는다. 확인된 사실과 개인적인 생각을 구분하고 확신하지 못하는 부분은 그 정도에 맞게 표현한다.
7. **길이와 형식을 내용에 맞춘다.** 짧게 끝나는 주제는 짧게 쓰고 복잡한 과정에는 설명을 충분히 쓴다. 소제목·목록·표는 구분이나 비교에 도움이 될 때 쓴다. ‘서론’과 ‘마치며’는 사용할 수 있지만 모든 글에 의무적으로 붙이지 않는다.
8. **경험담의 말투를 과장하지 않는다.** 원문에 있는 혼잣말, 괄호 속 덧붙임, 가벼운 자조와 농담은 살릴 수 있다. 기술 설명마다 감정이나 농담을 넣지는 않는다.

## 좋은 글의 기준

| 기준 | 확인할 내용 |
| --- | --- |
| 질문에 답했는가 | 읽고 나면 처음 궁금했던 점을 설명하거나 필요한 작업을 할 수 있다. |
| 설명이 이어지는가 | 결론에 도달하는 데 필요한 이유와 과정이 빠지지 않았다. |
| 구체적인가 | ‘좋다’, ‘빠르다’, ‘안전하다’고 평가했다면 어떤 조건에서 무엇이 달라지는지 설명했다. |
| 정확한가 | 기술 설명과 코드를 확인했고 적용 버전·조건·예외를 필요한 만큼 밝혔다. |
| 작성자의 판단이 보이는가 | 경험이나 의견을 다루는 글이라면 무엇을 겪고 왜 그렇게 생각했는지 알 수 있다. |
| 불필요한 반복이 없는가 | 같은 뜻을 표현만 바꿔 늘이지 않았다. 개념 이해에 필요한 재설명과 용어 반복은 남겼다. |

## 피해야 할 문체와 습관

- **설명을 대칭적인 구호로 바꾸지 않는다.** “정상은 조용히, 이상만 드러나게”, “위에서 요약, 아래로 원인”, “밀도가 기본, 여백은 구분에만”, “AI는 초안, 결정은 사람”처럼 압축하면서 행동과 조건을 생략하지 않는다. 무엇을 어떻게 한다는 뜻인지 풀어 쓴다.
- **문장을 습관적으로 둘씩 짝맞추지 않는다.** `A는 ~고, B는 ~이다`, `A이고, B합니다`도 점검한다. 실제 비교나 연결에 필요한 병렬문은 쓸 수 있다. 쉼표만 지우거나 두 문장으로 나누는 것으로 수정을 끝내지 않는다.
- **대조나 비례를 앞세운 소제목을 피한다.** “코드는 늘었는데 내가 따라가지 못했다”, “남겨두는 만큼 정할 것도 있다”처럼 `A했는데 B했다`, `A하는 만큼 B한다`로 대비를 만드는 표현도 점검한다. 해당 절에서 실제로 다루는 문제·행동·조건을 구체적으로 적는다. 본문에서도 추상적인 두 문장을 짝지어 의미를 만들지 않는다. 실제 사건의 인과관계와 기술적으로 필요한 비교까지 지우지는 않는다.
- **근거 없는 대조와 의미 부여를 피한다.** “단순한 X가 아니다”, “본질적인 변화다”, “새로운 가능성을 열었다”처럼 설명보다 평가가 앞서는 표현을 피한다. 반박할 오해나 변화의 근거가 있을 때 구체적으로 설명한다.
- **형식에 맞춰 내용을 채우지 않는다.** 항목을 세 개씩 맞추거나 모든 절을 같은 길이로 만들거나 모든 글을 교훈으로 끝내지 않는다. 굵은 글씨와 따옴표로 평범한 문장까지 강조하지 않는다.
- **지나치게 축약하거나 잘게 끊지 않는다.** “문제는 간단하다. 속도다. 그리고 신뢰다.”처럼 짧은 문장만 늘어놓지 않는다. 독자가 관계를 추측해야 한다면 원인·조건·결과를 연결해 설명한다.
- **예고와 요약으로 분량을 늘리지 않는다.** 안내 없이도 흐름을 이해할 수 있다면 “지금부터 자세히 알아보겠습니다” 같은 문구를 덜어낸다. 결론에서 본문 전체를 다시 말하지 않는다.
- **원문에 없던 경험과 확신을 추가하지 않는다.** 직접 해보지 않은 일을 경험담으로 쓰거나 확인하지 않은 수치를 넣거나 추측을 사실처럼 단정하지 않는다.
- **문체를 지나치게 매끈하게 통일하지 않는다.** 기술 용어를 반복하지 않으려고 부정확한 유의어로 바꾸지 않는다. 작성자의 의심이나 솔직한 판단을 상투적인 성공담으로 고치지 않는다. 오타와 문법 오류는 바로잡는다.

## 기존 글 재작성 절차

1. 원문의 핵심 질문, 경험, 의견, 결론을 확인한다. 기술적 오류를 고치는 과정에서 작성자의 경험이나 의견을 새로 만들지 않는다.
2. 필요한 근거를 공식 문서 등에서 조사하고 기술 설명과 예제를 확인한다. 실제로 실행하지 않은 코드를 실행했다고 쓰지 않는다. 출처와 적용 버전은 아래의 작성 시점 기준도 확인한다.
3. 문단 순서와 표현을 고친다. 당시 경험은 그 시점을 유지한다. 이후의 사건이나 새 기술을 당시 알고 있었던 것처럼 추가하지 않는다.
4. 원문과 비교해 생각과 의도가 달라지지 않았는지, 제목이 약속한 내용을 설명하는지, 코드와 예시가 설명에 맞는지 검토한다.
5. 원문과 메타데이터를 백업한 뒤 사용자가 요청한 글만 반영한다. 한 편 수정 요청을 전체 글 수정으로 확대하지 않는다.

## 작성 시점과 출처

- 최초 작성일을 유지하는 글은 그 날짜까지 공개된 자료와 기술 버전을 기준으로 쓴다. 원문에 날짜별로 남아 있는 후속 작업 기록은 그 날짜와 함께 보존한다.
- 새로 인용할 자료의 최초 발행일, 개정일, 적용 버전을 확인한다. 작성일보다 나중에 나온 글이나 명세는 당시 공개된 공식 자료로 교체한다.
- 계속 갱신되는 문서의 현재 화면만 보고 당시 내용이라고 가정하지 않는다. 공식 버전 문서, 릴리스 태그, 작성일 이전 커밋에 고정된 문서를 우선 사용한다. 날짜를 확인할 수 없으면 확인했다고 쓰지 않는다.
- 링크만 바꾸고 후대의 설명을 남기지 않는다. 이후에 도입된 API, 권고, 지원 중단 소식 등은 본문에서 제외하거나 작성 당시 내용으로 고친다. 기존 개념의 오류를 바로잡고 설명을 명료하게 만드는 작업은 계속한다.
- 본문에는 ‘재작성 시 추가’, ‘재작성 시 참고’ 등의 작업 안내를 넣지 않는다. 조사 시점과 출처 교체 이력은 별도 작업 기록에 남긴다.

## 본문 수정 시 보존할 정보

- 새 글을 만들거나 기존 글을 삭제하지 않고 같은 게시글 ID를 수정한다.
- 기본 변경 범위는 본문뿐이다. 제목, 주소(slug), 최초 작성일, 작성자, 카테고리, 태그, 조회수, 댓글, 기존 이미지를 보존한다. 수정일 갱신은 허용한다.
- 현재 MCP에서는 `blog_get_post`로 원문과 편집 필드를 읽은 뒤, `blog_update_post`에 기존 제목·주소·카테고리·태그를 그대로 넣고 `content`만 바꾼다.
- 현재 서버는 본문에서 빠진 이미지 파일을 삭제하므로 기존 이미지 URL을 유지한다. 이미지 삭제가 필요한 작업은 별도 요청 범위로 다룬다.
- 저장 직전에 원문이 달라지지 않았는지 다시 읽는다. 변경되었으면 새 원문을 바탕으로 수정안을 조정한다.
- 저장 후 본문 일치와 메타데이터 보존을 확인한다. 검증에는 조회수를 올리지 않는 관리자 조회와 목록 조회를 이용한다. 날짜 확인을 위해 일반 상세 조회를 불필요하게 호출하지 않는다.
